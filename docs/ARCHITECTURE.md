# Архитектура SynthOS

Документ описывает, как устроена система: от первого сектора диска до приглашения оболочки.

## Принципы

* **Всё своё.** Загрузчик, ядро, libc, драйверы, файловые системы, оболочка, VM и эмулятор DOS
  написаны в этом репозитории. Внешних зависимостей во время работы нет.
* **Переносимое ядро, тонкий HAL.** Весь код в `kernel/` — обычный C11 без привязки к x86.
  Всё железо спрятано за интерфейсом из `include/synth/hal.h` (~15 функций). Новая платформа
  (ARM-плата, калькулятор, RISC-V) = новая папка `arch/<платформа>/`, реализующая HAL.
* **Расширение без правки ядра.** Команды, файловые системы, форматы программ, настройки,
  приложения стола и функции Windows регистрируются макросами (`COMMAND`, `FS_TYPE`, `BINFMT`,
  `SETTING`, `GUI_APP`, `W32_EXPORTS`, `W64_EXPORTS`), которые кладут указатель
  на описание в отдельную секцию линковщика. Новый файл в `kernel/cmds/` — новая команда,
  без списков и `switch`.
* **Скорость.** Загрузка до приглашения — доли секунды. Консоль перерисовывает только
  изменившиеся строки, корень ФС живёт в памяти, диски работают через DMA крупными блоками с
  кэшем и отложенной записью. Каждое ускорение измеряется (`time`, `prof`, `winbench`, раздел
  «Скорость» ниже).

## Загрузка

```text
LBA 0          stage1 (MBR, 512 байт) + таблица разделов   arch/x86/boot/stage1.asm
LBA 1..16      stage2 (8 КБ)                                arch/x86/boot/stage2.asm
LBA 17..       ядро (плоский бинарник, заголовок SYNK,      build/*/kernel.bin
               код до 3.5 МБ в памяти) + пакет SYPK с ramdisk
               (вместе до ~3.75 МБ)
LBA 8192..     раздел EFI (4 МБ, тип 0xEF):                 build/*/esp.img
                 \EFI\BOOT\BOOTX64.EFI, \SYNTHOS\KERNEL.BIN
LBA 16384..    пакет программ SYNTHBDL (если есть:          build/*/chromium.bundle
               Chromium, tools/mkbundle.py), на диске
               «bundle0», распаковывается при первом входе
после пакета   раздел SynthFS (/home, тип 0x7F, до конца    форматируется при первой загрузке
               образа: 2 ГБ, файл разреженный)
```

Первый сектор системной области содержит, кроме кода stage1, маркер `SynthOS:` и **запись установки**
по смещению 416: `SYID`, 64-битный id и флаги (бит 0 — «установлена»). У образа id = 0, установщик
пишет новый случайный id. Загрузчики передают ядру в `x86_bootinfo` флаг `BOOT_SYSTEM`, начало
системной области (`system_lba`), её размер и id; ядро (`attach_boot_disk` в `arch/x86/hal.c`) ищет
диск, где по этому адресу лежит маркер с тем же id и заголовок ядра, — так флешка и установленная
копия не путаются. Если система стоит в разделе, он регистрируется как `system0`, а `bundle0` и
`data0` — внутри него.

**Путь BIOS.**

1. BIOS загружает **stage1** по адресу `0x7C00`. Тот читает stage2 в `0x7E00` через INT 13h —
   LBA-расширением, а на старых BIOS без него — по CHS (геометрия из AH=08h).
2. **stage2** включает линию A20, переходит в *unreal mode*, собирает карту памяти (E820, если нет —
   E801 или INT 15h/88h + INT 12h), читает заголовок ядра (`magic SYNK` + число секторов), копирует
   ядро на `0x100000`, заполняет `x86_bootinfo` по адресу `0x4F00` и переходит в защищённый режим.

**Путь UEFI** (`arch/x86/efi/`). Прошивка находит раздел 0xEF и запускает `BOOTX64.EFI` —
64-битное PE-приложение. Если на его томе есть `\SYNTHOS\SYSTEM.CFG` (установленная система:
`system=`, `sectors=`, `id=`, `register=`, `timeout=`), он при `register=1` добавляет себя в меню
загрузки прошивки (`Boot####` с короткой формой пути `HD(...)/File(...)`, первым в `BootOrder`) и
сбрасывает флаг, а затем показывает меню с другими системами — пунктами `BootOrder`, путь которых
ведёт на раздел диска; выбранная система запускается через `BootNext` и перезапуск. Без файла
(флешка) загрузчик ищет на других томах `SYSTEM.CFG` с `register=1`, регистрирует найденную
установку и запускает её загрузчик (`LoadImage`/`StartImage`). Потом он читает
`\SYNTHOS\KERNEL.BIN` с того же тома (Simple File System),
выбирает режим GOP (наибольший до 1920×1200), переводит карту памяти UEFI в формат E820, кладёт
`x86_bootinfo` (с полями фреймбуфера и флагом `BOOT_UEFI`) в страницу ниже 1 МиБ, вызывает
`ExitBootServices`, копирует ядро на 1 МиБ и прыгает в `trampoline.asm`: переход в режим
совместимости, выключение страниц, `EFER.LME` и `CR4.PAE` — и дальний переход в то же самое
32-битное ядро. Поэтому всё ядро, включая подсистему Windows, одинаково работает на BIOS и UEFI.

**Дальше общий путь.**

3. `arch/x86/entry.asm` обнуляет BSS, ставит стек и вызывает `x86_main()` (`arch/x86/hal.c`):
   GDT/IDT, PIC, таймер 1000 Гц, клавиатура, COM1, определение CPU (CPUID/TSC/FPU — всё
   необязательно, работает и на 486), затем страничная память и куча в самом большом свободном
   участке ОЗУ, затем дисплей: VGA-текст (BIOS) или графическая консоль (UEFI).
4. `kmain()` (`kernel/main.c`) — уже переносимый код: консоль → VFS → сетевая карта и первый
   запрос DHCP → ramfs + распаковка встроенного ramdisk → devfs → поиск диска → монтирование
   SynthFS в `/home` → файлы встроенных DLL в `/system/win32` → оболочка → стартовые скрипты →
   приветствие → REPL. Сеть запускается до дисков: линку нужна примерно секунда (e1000 в QEMU после
   записи RCTL секунду не принимает кадры), и она проходит, пока монтируется `/home`. Загрузка адреса
   не ждёт: первое соединение, DNS-запрос или `ping` сами ждут аренду до 4 секунд от старта
   (`net_await_address`). Свежий раздел размечается кусками по 64 КБ (битовая карта и таблица inode
   2-гигабайтного диска — 72 команды вместо ~9200). Повторная загрузка до оболочки в QEMU — 0,65 с.

Ramdisk — каталог `rootfs/` плюс собранные программы, упакованные утилитой `tools/mkrd` в формат
`SRD1` (сжатие LZ4) и дописанные после образа ядра пакетом `SYPK` (`mkrd --kernel`). Точка входа
переносит пакет на адрес 4 МБ, `setup_heap` (`arch/x86/hal.c`) начинает кучу с этого места и отдаёт
пакет ядру как `boot_info.initrd`, так что ramdisk не занимает место в нижних 4 МБ, где живёт код.

## HAL — граница с железом

`include/synth/hal.h`:

| Функция | Назначение |
|---|---|
| `hal_display()` | дисплей: размеры, `present()` для вывода ячеек, курсор, палитра, форма курсора; или потоковый `write()` |
| `hal_key_read(timeout)` | следующая клавиша (коды из `keys.h`) |
| `hal_key_repeat(delay, rate)` | автоповтор клавиш: USB — программный, PS/2 — команда typematic |
| `hal_ticks_ms`, `hal_sleep_ms`, `hal_rtc` | время |
| `hal_beep`, `hal_entropy` | звук, случайность |
| `hal_audio_open/space/write/close` | вывод 16-битного стерео PCM (AC'97 в `audio.c`: кольцо из 32 DMA-буферов, частота через VRA) |
| `hal_fs_init` | регистрация блочных устройств платформы |
| `hal_boot_disk`, `hal_system_sectors` | загрузочный диск и размер системной области — для установщика |
| `hal_graphics_enter(fb)`, `hal_graphics_leave` | графический режим для рабочего стола: линейный фреймбуфер (VBE через BIOS или GOP из UEFI) и возврат в текст |
| `hal_pointer_read`, `hal_pointer_present` | события мыши: сдвиг, колёсико, кнопки (PS/2, `mouse.c`) |
| `hal_in_interrupt` | идёт ли обработка прерывания (цикл событий GUI никогда не запускается из IRQ) |
| `hal_screen_count`, `hal_screen_*` | несколько мониторов и их режимы |
| `hal_net_init` | регистрация сетевых карт (`net_register`) |
| `hal_profile_start/stop` | сэмплирование адреса инструкции по таймеру для `prof` |
| `hal_reboot`, `hal_poweroff` | питание |
| `hal_arch`, `hal_machine` | названия для `fetch` |

Дисплей бывает **сеточный** (VGA и фреймбуфер: ядро держит буфер ячеек `{символ, атрибут}` и отдаёт
драйверу только изменённые строки) и **потоковый** (COM-порт: просто текст). Вся система работает в
обоих режимах; в потоковом недоступны только полноэкранные программы.

**Память x86** (`arch/x86/paging.c`): 0–4 МБ отображены один в один (ядро, таблицы, VGA), кроме
нулевой страницы — разыменование `NULL` ловится. Куча ядра видна с `0xC0000000` и физически
непрерывна (поэтому её буферы годятся для DMA, адрес — `vmm_phys`). `0x00400000–0xB0000000` —
пространство программ Windows, `0xB0000000–0xC0000000` — окно для регистров устройств
(`vmm_map_phys`: фреймбуфер, AHCI, NVMe, xHCI). Фреймбуфер отображается с write-combining
(`vmm_map_framebuffer`: запись PAT 1 = WC, страницы с PWT) — в виртуальных машинах и на железе
вывод кадра в видеопамять идёт пачками, а не по одной записи. Если процессор умеет **PAE**, таблицы становятся
трёхуровневыми: страницы ОЗУ выше 4 ГБ отдаются программам Windows кадрами (`vmm_frames_alloc`),
а 64-битные регистры устройств отображаются `vmm_map_phys64`. Большие диапазоны отображаются с
одним сбросом TLB вместо `invlpg` на каждую страницу.

**Long mode** (`cpu.c`, `long.asm`). Ядро остаётся 32-битным. Пока работает 64-битная программа,
`arch_long_enter` строит PML4 поверх тех же таблиц PAE и включает `EFER.LME`: ядро продолжает
выполняться в режиме совместимости (селектор `0x08`), программа — в 64-битном сегменте `0x30`,
`GS` указывает на TEB64 (`0x38`). Прерывания в 64-битном коде принимают отдельные заглушки IDT
(`isr64_*`), которые сохраняют `fxsave64` и строят обычный 32-битный `struct regs`.

**Адресные пространства и процессоры.** У каждого адресного пространства свои каталоги страниц
(`struct vmm_space`): записи ядра общие и при изменении переносятся во все пространства, записи
программ свои; `vmm_space_switch` меняет только корень (`CR3`). `hal_start_cpus` (`smp.c`) будит
остальные ядра: код `smpboot.asm` копируется в свободную страницу ниже 1 МБ, локальный APIC (xAPIC
или x2APIC) шлёт INIT и два SIPI, каждое ядро включает защищённый режим и страничную память ядра,
получает свой стек и копию GDT (`cpu_ap_init`) и ждёт в `ap_entry`. Сейчас ядра запускаются и
считаются (`Processors: N cores` при загрузке), но работу выполняет первое: ядро Windows-подсистемы
держит одно «текущее» состояние процесса (`W32_STATE`, TEB в GDT), и чтобы потоки шли на разных
ядрах, это состояние нужно сделать своим у каждого ядра и закрыть общие таблицы блокировками —
следующий шаг.

**Диски** (`hal_fs_init`): IDE (`ata.c`: bus-master DMA по 128 КБ за команду через контроллер PCI IDE,
PIO как запасной путь), AHCI (`ahci.c`, тоже 128 КБ за команду) и NVMe (`nvme.c`) через перебор PCI
(`pci.c`; 64-битный BAR выше 4 ГБ на шине 0 переносится в свободное место ниже 4 ГБ). Если загрузка
шла через BIOS и ни один драйвер не нашёл загрузочный диск, используется `biosdisk.c`: ядро
вызывает INT 13h через `biosthunk.asm` — выходит из страничного и защищённого режима, переключает
PIC и таймер на настройки BIOS, вызывает прерывание и возвращается (время, проведённое в BIOS,
досчитывается по TSC). Так `/home` сохраняется на USB-флешке и любом диске, который видит BIOS.
IDE и AHCI ждут конца команды по прерыванию (`cpu_wait`: `hlt`, а не опрос регистра — в ВМ каждое
чтение порта стоит выхода в гипервизор); сброс кэша AHCI — не чаще раза в секунду и при выключении.

**USB** (`xhci.c`, `usb.c`, `usbhub.c`, `usbhid.c`, `usbstor.c`): свой драйвер xHCI с кольцами
команд и событий, перечисление устройств через хабы, клавиатуры и мыши HID (boot protocol) и
флешки (Bulk-Only Transport + SCSI) как обычные блочные устройства — их разделы FAT сами
монтируются в `/mnt/…` (`automount.c`), при извлечении отключаются. `lsusb` — список устройств.

**Сеть** (`e1000.c` — Intel e1000/e1000e, `realtek.c` — RTL8139 и RTL8169): драйвер отдаёт
`struct netdev` с `send/receive/link`, остальное делает переносимый стек в `kernel/net/`.
e1000 возвращает дескрипторы приёма пачками по 16, TCP подтверждает каждый второй сегмент (остаток —
в `tcp_tick`), `net_wait` спит, только если не пришло ни одного кадра.

## Консоль и темы

`kernel/core/console.c` — терминал поверх дисплея: перенос строк, прокрутка, табуляция, подмножество
ANSI-последовательностей (цвета SGR, позиционирование), статус-бар, «удержание» вывода для
пакетной перерисовки.

Цвет ячейки — 4 бита текста + 4 бита фона, это **индексы палитры** из 16 цветов.
Тема (`kernel/core/theme.c`) задаёт:

* `palette[16]` — RGB-значения индексов (на VGA программируются регистры DAC, поэтому смена темы
  мгновенно перекрашивает уже выведенный текст);
* `roles[]` — атрибут для каждой «роли» интерфейса: `text`, `accent`, `error`, `dir`,
  `prompt.path`, `syntax.command`, `status` и т. д.

Код никогда не использует цвета напрямую — только роли (`con_role(ROLE_ERROR)`) или разметку
`{accent}текст{/}`. Файлы тем — `/etc/themes/*.theme` (формат `ключ = значение`, см. `sunset.theme`).

**Шрифт.** `kernel/core/font8x16.c` — свой растровый шрифт 8×16 для кодовых страниц 437 и 866,
сгенерированный `tools/mkfont.py` из DejaVu Sans Mono (рамки и блоки рисуются программно, чтобы
стыковаться без зазоров). В VGA-режиме он загружается в знакогенератор (плоскость 2), поэтому
кириллица работает и на BIOS-машинах; `kernel/core/fbcon.c` рисует им консоль на фреймбуфере
UEFI (32/24/16 бит, ×2 на экранах от 1600×1000) и перерисовывает только изменившиеся ячейки.

## Рабочий стол

`kernel/gui/` — графический интерфейс поверх линейного фреймбуфера. Слои:

* **`gfx.c`** — рисование в `struct canvas` (пиксели XRGB, шаг строки, прямоугольник отсечения):
  заливки и градиенты с альфа-смешиванием, скруглённые прямоугольники со сглаживанием, мягкие тени,
  линии, круги, значки, текст. Шрифты интерфейса (`uifont.c`) — Inter и DejaVu, предрастеризованные
  `tools/mkuifont.py` в 4-битную альфу (латиница, кириллица, символы); значки (`icons.c`) — из
  `tools/mkicons.py`, упакованы LZ4.
* **`wm.c`** — оконный менеджер и композитор. У каждого окна своя поверхность; рамки, кнопки-«светофоры»,
  тени и всплывающие окна рисуются при сборке кадра в задний буфер. Перерисовываются только
  «грязные» прямоугольники, затем они копируются во фреймбуфер каждого монитора с преобразованием
  в 32/24/16 бит. Мониторы образуют общее пространство (`wm_screen_rect`), у каждого своё разрешение.
  **Курсор не входит в задний буфер**: прерывание мыши (PS/2 и такт опроса USB) через `hal_pointer_hook`
  само считает новое положение (ускорение, края экранов), кладёт его в событие (`placed`) и сразу рисует
  стрелку прямо во фреймбуфере, возвращая то, что она закрывала, из заднего буфера (`hw_cursor_move`).
  Пока кадр копируется (`fb_busy`), прерывание только отмечает перемещение, и оно делается сразу после.
  Поэтому указатель движется плавно, даже когда цикл стола занят долгой командой или программой.
  **`glass.c`** — «жидкое стекло»: фон под панелью уменьшается и размывается один раз (`capture`), затем
  каждый пиксель берётся со смещением по нормали к краю — профиль выпуклой линзы посчитан по закону
  Снелла (`refract_lut`), так что у кромки фон преломляется и «затягивается» внутрь; каналы R/G/B
  смещаются чуть по-разному (дисперсия), сверху добавляется блик по направлению света и подсветка у
  указателя мыши. Геометрия края и готовый результат кэшируются (`geo`, `out`) и пересчитываются, только
  если изменился фон, размер, вид или позиция мыши рядом. Варианты: Liquid Glass, Frosted, Solid.
  У жидкого стекла два снимка фона: размытый в 8 раз меньший для середины и чёткий вдвое меньший для
  кромки — линза у края показывает фон резким и переходит в матовое внутри; блик по кромке с двух
  сторон и чуть затемнённая полоса преломления дают толщину. Стекло произвольной формы может дать
  `shape_sdf` (расстояние до края и нормаль), тогда и оно преломляет. Яркость стекла подстраивается под
  фон (средняя яркость снимка), чтобы текст на нём читался и над тёмной фотографией.
  **Анимации** (`anim.c` — кривые, `wm.c` — «призраки»): при открытии, закрытии, сворачивании,
  разворачивании и развёртывании на весь экран снимается снимок окна (`snapshot`), и несколько кадров
  рисуется он — с масштабом и прозрачностью, «джинном» в Dock (каждая строка сжимается по своей кривой)
  или плавным переходом между размерами; само окно в это время «придержано» (`anim_hold`). Время идёт
  по часам, поэтому на медленной машине кадров просто меньше. `config animations off` выключает всё.
  `wmbench` меряет время кадра композитора, `wmstat [секунды]` — сколько кадров, пикселей и пересчётов
  стекла было за это время (удобно вместе с `prof`).
  **Чтобы не тормозило в виртуальной машине (TCG):** перерисовывается только то, что изменилось (Dock
  считает старые и новые прямоугольники значков и подсказки, окна сообщают повреждения со своим `z` через
  `wm_damage_client`, поэтому вывод терминала не трогает стекло под ним); пока окно тащат или идёт
  анимация, стекло над ним держит старое размытие (`glass_defer`) и догоняет в конце; покрытие фигуры
  считается один раз на пиксель (с полными отрезками строк), точки выборки — один раз на кадр, а
  внутренние пиксели стекла считаются парами. Погода спрашивает DNS без ожидания
  (`net_resolve_start`/`net_resolve_poll`).
* **`ui.c`** — виджеты в стиле immediate mode: функция-кадр приложения вызывается и для рисования
  (`ui->c`), и для событий (`ui->e`); идентификаторы виджетов — порядковые номера вызова, состояние
  (`hot`/`active`/`focus`) хранится в `struct ui_state` окна. Кнопки, флажки, переключатели,
  ползунки, поля ввода, списки, меню, диалоги, боковые панели и группы настроек.
* **`menubar.c`** (меню активного приложения, часы, статус), **`dock.c`** (закреплённые и запущенные
  приложения, корзина), **`spotlight.c`** (поиск Ctrl+Space и Launchpad), **`lock.c`** (вход и
  блокировка), **`wallpaper.c`**, **`desktop.c`** (значки дисков, горячие клавиши, уведомления,
  цикл событий, команды `desktop`/`launch`), **`clock.c`** (вид часов: 24/12 часов, секунды, дата;
  время берётся из `time_local()` — RTC в UTC плюс `config timezone`).
* **`apps/settings.c`** — Системные настройки. Панели — функции, которые строят строки через
  `section/row/toggle/choice/popup/slider/field/link`; каждая панель проходится дважды за кадр:
  измерительный проход (без холста и событий) узнаёт высоту групп и считает строки, совпавшие с
  поиском, затем настоящий проход рисует группы и строки и обрабатывает ввод. Поиск так же проходит
  все панели и оставляет в боковой панели только те, где есть совпадения.
* **`terminal.c`** — дисплей консоли (`struct display`), который рисует ячейки шрифтом 8×16 в окно
  не чаще раза в 33 мс; через него работает обычная оболочка. Тема консоли `mirage` переключается
  на `mirage-light`, когда стол светлый, так что терминал всегда в тон системе.

**Образы** (`look.c`). `struct gui_look` задаёт оттенок, акцент, светлый или тёмный режим, обои и
раскладку оболочки: вид Dock (`DOCK_CENTER`, `DOCK_CORNER`, `DOCK_RAIL`), где статус
(`STATUS_MENUBAR`, `STATUS_PILL`), есть ли панель «Места» и какие виджеты стоят на
столе. Палитра `style` выводится из оттенка (`gui_style_refresh`), стекло подкрашивается им же;
смена образа пересобирает оболочку (`chrome_stop/start`, `widgets_start`) под кроссфейдом всего
экрана (`wm_crossfade`). Рабочая область окон (`wm_work_area`) учитывает строку меню, капсулу
статуса, ленту и «Места».

**Оболочка.** `dock.c` строит один список элементов и раскладывает его по-разному: ряд по центру
с увеличением, угловую панель с вогнутыми скруглениями (стекло произвольной формы — у `glass_look`
есть функция покрытия `shape`, кромка подсвечивается по разнице покрытий), вертикальную ленту,
раскрывающуюся с подписями. `panel.c` — капсула статуса и панель «Места». Все движения — пружины `anim.c`
(`spring_step`: жёсткость и затухание, время по часам), их шагает `wm_animate` из насоса.

**Своё у каждого образа.** `look.c` хранит копии образов пользователя (`~/.looks`: вид Dock, статус, «Места»),
`dock.c` — значки Dock по образам (`~/.dock`: имена приложений или пути к файлам), `widgets.c` — виджеты
(`~/.widgets`). Перетаскивание: значок, поднятый с Dock или со стола (`desktop_icon_drag` → `dock_drag_move`),
рисуется над всем (`dock_paint_drag`); в Dock вставляется элемент-промежуток `DI_GAP` там, куда упадёт значок, а
`rebuild_glide` после пересборки запускает пружины смещения от старых мест к новым. Виджеты стоят столбцом
(`place_all`), позиции — тоже пружины; режим редактирования прячет окна (`wm_peek_desktop`) и открывает галерею.
**Keep on Top**: флаг `WIN_PINNED`; `restack` устойчиво раскладывает список окон слоями — обычные, закреплённые,
всплывающие — и только потом раздаёт `z`.

**Окна.** Заголовок — три точки (раскрашиваются и растут под курсором), название и кнопка «⋯»:
`wm_window_menu` собирает в одно меню разделы `app_menu` окна (заголовки — `MENU_HEADER`) и действия
окна. Приложения поэтому не держат своих панелей инструментов: Блокнот — только текст, Файлы —
только содержимое (поиск набором), Фото и Видео — только картинка.

**Виджеты** (`widgets.c`) рисуются на слое стола под окнами, каждый на своём стекле (`z` между столом
и окнами, так что окна над ними стекло не сбрасывают). Погода — неблокирующий HTTP к wttr.in прямо на
сокетах; задачи — `~/.tasks`. **Медиа** (`media.c`): синтезатор (осцилляторы на таблицах, огибающие,
секвенсор шагов, эхо) играет встроенные песни, WAV и звук из AVI идут через тот же вывод; уровни полос
для визуализатора берутся из голосов синтезатора или из фильтров потока. **Картинки** — `kernel/lib/`:
`png.c` (все типы цвета, Adam7), `jpeg.c` (baseline и progressive, любая субдискретизация, рестарты),
`gif.c` (LZW, кадры анимации), `picture.c` (BMP и общий вход `picture_load`).

**Установка** (`kernel/core/install.c`) идёт шагами (`install_step`), чтобы окно мастера жило.
На весь диск системная область (MBR, stage2, ядро с ramdisk, раздел EFI) и пакет программ
копируются как есть, третий раздел таблицы растягивается до конца диска. В свободное место или
вместо раздела `parttab.c` сначала правит таблицу (MBR — четыре записи; GPT — запись, CRC32
массива и заголовка, резервная копия в конце диска пишется первой), создавая раздел EFI на 4 МБ и
раздел SynthOS; в первый копируется раздел EFI образа, во второй — загрузочная область и пакет.
Затем пишется запись установки с новым id, обнуляется начало раздела данных (первая загрузка сама
отформатирует SynthFS) или он форматируется сразу и туда копируется `/home`, и на новый раздел EFI
кладётся `SYSTEM.CFG` с `register=1`. Мастер первого запуска (`kernel/gui/setup.c`) показывается,
пока нет `/home/.setup-done`; при загрузке с USB-флешки — экран «Try / Install» (`/home/.live-welcome`).

**Цикл событий кооперативный.** `gui_run` переключает графику, открывает окно терминала, делает его
дисплеем консоли (`con_init`) и ставит «насос» `input_set_pump(pump)`, после чего просто вызывает
`shell_repl`. Каждый раз, когда оболочка или программа ждёт клавишу (`input_getkey`/`input_poll`),
вызывается насос: он читает клавиатуру и мышь, раздаёт события окнам, обрабатывает таймеры и
перерисовывает экран, а клавиши для терминала кладёт в очередь `input_inject`. Программы Windows
с окнами крутят тот же насос в своём цикле сообщений. Долгая операция без ввода «замораживает» стол
до своего завершения (браузер, например, показывает ход загрузки, перерисовывая окно сам).

Приложения (`kernel/gui/apps/`) регистрируются `GUI_APP` (секция `synth_gui_apps`) и находятся по
имени или началу слова (`launch mon` → System Monitor); поле `extensions` связывает их с типами
файлов в Файлах. Плавающая точка — только в `calc_fp.c` (правило `*_fp.c`).

**Chrome** (`apps/chrome.c`) — браузер системы: запускает настоящий Google Chrome из `/home/apps/chrome`, а
если его ещё нет — окно «Get Chrome». Установка (`chrome_install`, `kernel/cmds/omaha.c`) спрашивает сервер
обновлений Google по протоколу Omaha 3.1, скачивает CRX3-пакет офлайн-установщика (проверка SHA-256 и
свободного места), находит в нём установщик (хранимый член zip), в установщике — 7z-архив и распаковывает
`Chrome-bin/` прямо из скачанного файла (`kernel/lib/sevenzip.c` + `lzma.c`: сжатые заголовки, граф кодеров
Copy/LZMA/BCJ2, хранимые файлы пишутся потоком по 1 МБ). Пакет качается сжатым gzip (231 МБ вместо 443 МБ)
и распаковывается на лету, SHA-256 считается по распакованному. Работа идёт из цикла стола, а обратный вызов
прогресса подкачивает события (`input_poll`) и даёт поработать программам Windows (`w32_background`), так
что во время загрузки стол живой. Через 15 секунд после входа, если есть сеть и место, Chrome начинает
качаться сам, в фоне (`chrome_auto_arm`, `config chromeauto off` — выключить); ход виден полоской под
значком в Dock (`gui_app_progress`). Окна chrome.exe
привязываются к приложению Chrome (`gui_app_for_program`), поэтому в Dock это один значок с настоящей
иконкой из exe. HTML-движок (`html_parse`) остался для команды `browse`.

## Файловая система

`kernel/fs/vfs.c` — VFS с vnode, счётчиком ссылок и таблицей монтирования (поиск самого длинного
префикса). Пути нормализуются лексически (`path_resolve`). Драйвер реализует `struct vnode_ops`
(lookup/create/unlink/rename/readdir/read/write/truncate/stat/release) и регистрируется `FS_TYPE`.

* **ramfs** — дерево в памяти, корень системы.
* **devfs** — `/dev/null`, `zero`, `random`, `console`.
* **SynthFS** (`kernel/fs/sfs.c`) — дисковая ФС: суперблок, битовая карта блоков, таблица
  inode по 64 байта (10 прямых блоков + косвенный + двойной косвенный, файл до ~8 МБ),
  каталоги из записей по 64 байта, кэш блоков. Данные файла читаются и пишутся непрерывными
  участками до 256 блоков одной командой, полностью перезаписываемые блоки не обнуляются;
  при записи файла битовая карта и изменённые блоки кэша
  записываются в конце, а не после каждого блока. Мелкое чтение обычного файла подтягивает
  до 64 КБ его следующих соседних блоков одной командой (упреждающее чтение; запись в эти блоки
  его сбрасывает) — команда диска стоит почти одинаково при любом размере. Кэш метаданных —
  128 блоков, 4-канальный (таблицы разных уровней большого файла больше не вытесняют друг друга
  на каждом блоке), поиск свободного inode начинается с запомненного места, а не с начала таблицы.
  На запуске Chromium это 12 тыс. команд диска вместо 260 тыс.: `chrome.exe --headless` в QEMU
  без KVM — 62 с вместо 235 с, `sha256sum chrome.dll` (287 МБ) — 23 с вместо 110 с.
* **FAT12/16/32** (`kernel/fs/fat.c`) с длинными именами (VFAT): флешки, разделы Windows, второй
  диск в тестах. Данные читаются и пишутся непрерывными цепочками кластеров одним запросом;
  последовательная запись копится в буфере 64 КБ; секторы FAT и каталогов лежат в LRU-кэше
  и записываются при закрытии файла, вытеснении и операциях с каталогами (две копии FAT больше
  не вытесняют друг друга). `automount.c` разбирает MBR/GPT и монтирует найденные тома.
* Блочные устройства — `kernel/core/block.c` (`block_register`, разделы через смещение).

Безопасность: драйвер x86 подключает раздел `data0` только если на диске лежит именно загрузочный
образ SynthOS (сигнатура в MBR + заголовок ядра), поэтому чужие диски никогда не форматируются.

**Раскладка в стиле Windows** (`kernel/core/winpath.c`). Каталоги SynthOS и пути Windows
сопоставляются таблицей правил (порядок важен — от частного к общему):

| Windows | SynthOS |
|---|---|
| `C:\Windows\System32` | `/system/win32` (файлы-маркеры встроенных DLL) |
| `C:\Windows` | `/system` |
| `C:\Program Files`, `C:\Program Files (x86)` | `/apps` |
| `C:\ProgramData` | `/system/data` |
| `C:\Users\<любое имя>`, `C:\Users` | `/home` |
| `C:\Windows\Temp`, `C:\Temp` | `/tmp` |
| `C:\` | `/` |
| `D:` … `Y:` | `/mnt/d` … `/mnt/y` |

Имена ищутся без учёта регистра (`vfs_resolve_nocase`). Эти правила используют подсистема
Windows, эмулятор DOS, оболочка (любой аргумент вида `C:\…`) и команды `drives`/`winpath`.

* `kernel/shell/lineedit.c` — редактор строки: курсор, история, Tab-дополнение, подсказка из

## Запуск программ

`kernel/exec/exec.c` ищет файл в текущем каталоге и `PATH`, пробуя расширения из `PATHEXT`,
затем выбирает формат по `probe()` зарегистрированных `BINFMT`:

| Формат | Где | Как работает |
|---|---|---|
| `sx` | `kernel/vm/` | байт-код SynthOS для VM |
| `mz`, `com` | `kernel/dos/` | эмуляция 8086 + сервисы DOS/BIOS |
| `pe` | `kernel/win32/` | программы Windows (PE32 и PE32+), выполняются процессором напрямую |
| `script` | `kernel/exec/script.c` | скрипт оболочки (`.sh`, `#!`) |

### Виртуальная машина SX

32-битная регистровая машина: 16 регистров, флаги сравнения, линейная память программы с защитой
от выхода за границы и от обращения к нулевой странице. Инструкция — 4 байта
`[opcode][a][b][c]` плюс необязательное 32-битное значение; старший бит opcode означает «последний
операнд — число». Таблица инструкций одна на ассемблер, дизассемблер и интерпретатор
(`kernel/vm/opcodes.c`). Системные вызовы — `sys имя` (вывод, файлы, клавиатура, экран, время).
Ассемблер (`kernel/vm/asm.c`) двухпроходный, работает и внутри ОС (`asm`), и на хосте при сборке
(`tools/sasm.c` компилирует тот же исходник). Формат файла: заголовок 24 байта
(`SYNX`, версия, точка входа, размер кода, размер памяти) + код.

### Эмулятор MS-DOS

* `cpu.c` — интерпретатор 8086/80186 (все инструкции, префиксы, строковые операции с REP,
  BCD, ENTER/LEAVE, PUSHA/POPA…). Векторы прерываний указывают на заглушки в сегменте `F000`
  вида `F1 nn CF`: опкод `F1` передаёт управление в C-обработчик, поэтому программы могут
  перехватывать прерывания и вызывать старые обработчики, как на настоящем ПК.
* `dos.c` — 1 МБ памяти, цепочка MCB, PSP, окружение, загрузка `.COM` и `.EXE` с релокациями,
  вложенный запуск (`INT 21h/4Bh`), таймер 18.2 Гц (INT 8 → INT 1Ch), порты.
* `int21.c` — функции DOS: консоль, файлы, каталоги, поиск файлов, память, дата/время, IOCTL.
  Диск `C:` = корень SynthOS, имена сопоставляются без учёта регистра. `COMMAND.COM /C`
  выполняет команды оболочки SynthOS.
* `bios.c` — INT 10h/16h/1Ah/15h и видео. Пока программа печатает через DOS, вывод идёт в
  обычную консоль (и может быть перенаправлен в файл). Как только она обращается к видеопамяти
  или позиционирует курсор, включается «экранный режим»: область 80×25 из `B800:0000`
  синхронизируется с консолью по изменениям, а палитра временно переключается на стандартную VGA.

### Подсистема Windows

Программа Windows исполняется самим процессором; ядро лишь подготавливает ей мир, похожий на
Windows, и отвечает на вызовы API.

* **Процесс** (`process.c`). Для программы отводится арена — участок кучи ядра, отображённый с
  `0x20000000` (3/4 свободной памяти, минимум 1 МБ); в ней своя куча (`struct heap`), стек, TEB и
  PEB (версия 10.0.19045, параметры процесса, командная строка, окружение). Сегмент `FS`
  (селектор `0x18` в GDT) указывает на TEB, как в Windows. Вход в код программы — `arch_w32_call`
  (`win32.asm`): сохраняет регистры ядра, переключает стек и `FS`; выход (`ExitProcess`, сбой,
  Ctrl+C) — `arch_w32_abort` возвращает управление ядру из любой глубины.
* **Загрузчик** (`pe.c`). Образ кладётся по своему базовому адресу (или переносится по
  релокациям), заполняются импорты (по имени и ординалу), поддерживаются форвардеры, TLS-колбэки,
  `DllMain`, DLL рядом с программой, в текущем каталоге, `C:\Windows\System32` и `C:\Program Files`.
  Встроенные DLL (`kernel32`, `msvcrt`, …; `api-ms-win-*`, `ucrtbase`, `msvcr*` — псевдонимы)
  получают фиктивный PE-заголовок, чтобы `GetModuleHandle`/`GetProcAddress` работали как обычно.
  Неизвестная функция связывается с заглушкой, которая аккуратно завершает программу с её именем.
* **API** — обычные C-функции с `__attribute__((stdcall))`, зарегистрированные таблицами
  `W32_EXPORTS` в секции `synth_win32`; одну DLL могут собирать несколько файлов
  (`kernel32.c` — процесс/память/синхронизация/SEH, `files.c` — файлы и окружение, `console.c`,
  `locale.c`, `user32.c`, `system.c`). `kernel/win32/crt/` — своя msvcrt: структура `FILE`
  совместима с MSVC (`_iob`), текстовый/двоичный режим, буферизация, `printf`/`scanf` с плавающей
  точкой на x87 (файлы `*_fp.c` собираются с `-m80387`), математика, время, conio.
* **Консоль**: атрибуты Windows совпадают по битам с VGA-атрибутами, поэтому цвета программ
  отображаются через палитру текущей темы. Вывод в другой кодировке (`SetConsoleOutputCP(65001)`
  и т. п.) перекодируется в текущую кодовую страницу консоли.
* **Исключения**: `RaiseException` проходит цепочку SEH по `FS:[0]`, `RtlUnwind` раскручивает её;
  C++-исключения MinGW (DWARF) работают внутри самой программы. Сбой процессора (обращение по
  `NULL`, деление на ноль) завершает программу с кодом Windows (`0xC0000005` …) и сообщением.
* **Окна** (`window.c`, `gdi.c`, `controls.c`, `dialog.c`, `resource.c`): окно Windows — это окно
  `wm.c` со своей поверхностью; `WM_PAINT`, сообщения мыши и клавиатуры, таймеры, классы и
  оконные процедуры, GDI (перья, кисти, шрифты, битмапы, DIB-секции, `BitBlt`), стандартные
  элементы (кнопки, поля, списки) и диалоги из ресурсов `.rc`. Всплывающие окна без заголовка (меню,
  пузыри, подсказки, списки `<select>`) — `WIN_BARE`: без рамки, кнопок, тени и анимации, ровно там, где
  их ставит программа; `WS_EX_NOACTIVATE` (`WIN_NOACTIVATE`) — ни показ, ни щелчок не забирают фокус
  у окна-хозяина (иначе Chromium сразу закрывает меню). Слоёные окна получают картинку через
  `UpdateLayeredWindow` (предумноженная альфа переводится в обычную, окно смешивается по альфе —
  `WIN_TRANSLUCENT`); `CreateDIBSection` с секцией строит битмап прямо на общей памяти, в которую рисует
  компоновщик Chromium.
* **Диалоги файлов** (`filedialog.c`, `kernel/gui/picker.c`): `IFileOpenDialog`/`IFileSaveDialog`
  (`CoCreateInstance`), `IShellItem`, `SHCreateItemFromParsingName`, `GetOpenFileName`/`GetSaveFileName`
  показывают панель рабочего стола `gui_file_picker` и ждут её, как модальный диалог, разбирая
  сообщения программы.
* **Потоки** (`thread.c`): у каждого потока свой стек и TEB; переключение — по таймеру каждые
  10 мс, пока выполняется код программы, и в ожиданиях (`WaitForSingleObject`, `Sleep`, критические
  секции, события, мьютексы, семафоры, SRW-блокировки, условные переменные). Ожидание описывает, чего
  ждёт поток (`struct w32_wait`): объекты ядра, слово в памяти (блокировки, условные переменные,
  `WaitOnAddress`), сообщения и I/O своего процесса, данные из сети, срок. Планировщик проверяет это
  сам, не переключаясь на поток, и будит его, только когда условие могло выполниться: блокировки
  будят лишь потоки своего процесса, данные в канале — один поток процесса-читателя (он завершает
  ожидающий I/O), сообщения и события рабочего стола — процесс окна. Остальные ожидания (редкие)
  перепроверяются, как раньше, а ожидания процесса раз в 250 мс — на всякий случай (`schedstat 5`
  пишет «missed wake», если поток получил своё только после такой перепроверки). Поток, чьё ожидание
  закончилось, выполняется раньше занятых, а пакеты из сети забираются и по таймеру, пока программа
  считает, — поток, который их ждёт, выполняется следующим. Простаивающий
  Chromium делает ~1300 переключений в секунду вместо ~10000. `schedstat` показывает счётчики,
  `schedstat 10` пишет их в журнал каждые 10 с вместе с местами ожиданий и причинами пробуждений;
  `config w32precise off` возвращает старое поведение для сравнения.
* **Состояние процесса**: глобальные переменные с `W32_STATE` копируются при каждом переключении между
  процессами, поэтому крупные таблицы (очередь сообщений, таймеры, зарегистрированные сообщения,
  отображения файлов) лежат в куче программы, а в секции — только указатели (41 → 9.5 КБ).
  Переключение адресного пространства переписывает только записи каталога страниц, которые хоть раз
  были у одного из двух пространств.
* **Фоновые программы** (`w32_start`, `w32_background` в `process.c`): оконная программа, открытая с
  рабочего стола (двойной щелчок по `.exe` или ярлыку `.lnk`), не занимает терминал. Пока оболочка
  ждёт ввода, «насос» рабочего стола на время ставит в кольцо процессов процесс-хозяин со стеком
  оболочки: программы выполняются, а хозяин получает управление, когда им нечего делать (или по
  таймеру), и возвращает его оболочке. Ctrl+C таких программ не прерывает.
* **Chromium**: дочерним процессам `chrome.exe` (`--type=…`) добавляется `--ipc-connection-timeout=600`:
  иначе процесс, к которому браузер не подключился за 15 секунд (на медленной машине — служба сети),
  завершается, и страницы перестают грузиться.
* **Рамка окна** (`window.c`): программы, которые рисуют свои кнопки «свернуть/развернуть/закрыть»
  (Chromium, Electron), отвечают на `WM_NCHITTEST` кодами `HTMINBUTTON`/`HTMAXBUTTON`/`HTCLOSE`;
  поток окна опрашивает эти коды после создания и изменения размера, область кнопок закрашивается
  цветом соседних пикселей, а щелчки в неё не передаются — остаются кнопки заголовка ОС.
* **Сеть** (`winsock.c`, `inet.c`): ws2_32 поверх сокетов ядра (TCP/UDP, `select`, `WSAPoll`,
  `getaddrinfo`); wininet, winhttp и `URLDownloadToFile` поверх `http_fetch`, то есть с HTTPS,
  редиректами и cookies.
* **UCRT** (`crt/ucrt.c`): `__stdio_common_*`, `_initialize_onexit_table` и остальные функции
  `api-ms-win-crt-*`; `vcruntime140` и `ucrtbase` — псевдонимы msvcrt.
* **Вложенный запуск** (`system()`, `CreateProcess`, `ShellExecute`): вызов уходит на отдельный стек
  ядра, отображения родителя (арена и образы) снимаются, а состояние модулей (всё, что помечено
  `W32_STATE`, лежит в секции `w32state`) копируется в сторону; после завершения дочерней программы
  всё возвращается. Так одна Windows-программа может запустить другую.

### 64-битные программы Windows

Загрузчик понимает PE32+ (64-битная база, релокации `DIR64`, 64-битная IAT). Ядро не
переписано под x86-64: все функции API остаются 32-битными, а 64-битная программа видит их
через заглушки импорта `mov r11d, описание; jmp w64_gate`. `w64_gate` (`long.asm`) сохраняет
неизменяемые регистры и `xmm6–15`, дальним возвратом переходит в 32-битный сегмент ядра и вызывает
диспетчер `w64_dispatch_fn(описание, целые аргументы, xmm-аргументы)`. Таблицы `W64_EXPORTS`
описывают, как переложить аргументы: обрезать до 32 бит, разобрать `printf` с 8-байтными слотами
(`W64F_FMT`), обернуть `FILE*` в 64-битный прокси с раскладкой MSVC x64 (`W64F_FILE`), вернуть
64-битное значение, вызвать математику с `xmm0`, или вызвать свою обёртку, переводящую структуры
(`WNDCLASSEX`, `MSG`, `CREATESTRUCT`, `addrinfo`, `fd_set`…). Указатели из кучи ядра
(`0xC0000000+`) расширяются без знака. Обратные вызовы в 64-битный код (оконные процедуры,
`qsort`, потоки, TLS-колбэки) идут через `arch_w64_call`.

Исключения x64 — табличные: `win64seh.c` раскручивает стек по `.pdata`/`UNWIND_INFO`, выполняет
двухфазную обработку с языковыми обработчиками (C++ MinGW/MSVC), коллизии раскрутки и
`RtlCaptureContext`/`RtlRestoreContext`/`RtlUnwindEx` на ассемблере.

## Сеть и интернет

```text
программа / браузер / wget / WinINet
        │ http_fetch (redirect, chunked, cookies, прогресс, отмена)     kernel/net/http.c
        ▼
  TLS 1.3 / 1.2 + проверка X.509 по /etc/certs и /home/certs           kernel/net/tls.c, x509.c
        │ X25519, P-256/384, AES-GCM, ChaCha20-Poly1305, SHA-2, RSA     kernel/crypto/
        ▼
  сокеты: TCP (масштаб окна, повторы, RST, сегменты не по порядку), UDP  kernel/net/socket.c, tcp.c
        ▼
  IPv4, ARP, ICMP, DHCP, DNS                                           kernel/net/core.c, dhcp.c, dns.c
        ▼
  struct netdev ← e1000 / RTL8139 / RTL8169                            arch/x86/
```

* Стек работает опросом: `net_poll` вызывается из циклов ожидания ядра (`hal_set_idle`), поэтому
  никаких прерываний сетевой карты и потоков ядра не нужно.
* **TLS** (`tls.c`): клиент TLS 1.3 (HelloRetryRequest, наборы 1301/1302/1303, группы X25519, P-256,
  P-384) с откатом на TLS 1.2 (ECDHE с RSA или ECDSA, AES-GCM и ChaCha20-Poly1305, extended master
  secret, защита от понижения версии). Сертификат сервера проверяется по цепочке до доверенного
  корня, по имени (SAN, маски `*.`) и сроку действия; подписи RSA PKCS#1/PSS и ECDSA.
* **Случайность** — DRBG на ChaCha20, который подпитывается `hal_entropy` (TSC и счётчик таймера).
* **TCP** (`tcp.c`): масштабирование окна (сдвиг 5); буфер приёма начинается с 64 КБ и при большой
  загрузке растёт до 1 МБ, так что далёкий сервер держит в пути полное окно; сегменты, пришедшие раньше
  предыдущих, ждут в очереди (`ahead`), а не отбрасываются.
* **AES-GCM**: GHASH с 8-битными таблицами Шоупа на 32-битных словах (одна выборка на байт).
* **HTTP** (`http.c`): с флагом `HTTP_GZIP` просит `Content-Encoding: gzip` и распаковывает ответ на лету
  (`gunzip_stream` в `inflate.c`: декодер останавливается на границе символа, когда во входе меньше
  запаса, и продолжает со следующим куском; последние 32 КБ вывода остаются окном). HTTP/1.1 с
  `Connection: close`, до 8 редиректов, chunked, POST, свои
  заголовки, прогресс, отмена по Ctrl+C; общий **cookie-jar** в памяти (домен, путь, `Secure`,
  `Max-Age`/истечение) для браузера, `wget`, `browse` и программ Windows.
* **HTML** (`html.c`): токенизатор с сущностями и кодировками (UTF-8, windows-1251/1252, latin1),
  пропуск `script/style/svg` и скрытых элементов, блоки и отступы, списки, таблицы, `pre`, ссылки
  относительно `<base>`, формы с полями всех основных типов.

## Скорость

Инструменты: `time команда`; `prof [-o файл] команда` — таймер (1000 Гц) записывает адрес
прерванной инструкции, `tools/profsym.py` сводит адреса в функции ядра; `prof start` … `prof -k stop`
профилирует в фоне (пока работает Chromium) и пишет отчёт в журнал ядра, `prof -c` относит время
ядра к вызывающей функции (кто вызывает `memcpy`); `schedstat` — переключения и ожидания потоков; `winbench` — консоль, файлы,
куча, `sprintf`, вызовы API из настоящей Windows-программы.

Что было найдено и исправлено (QEMU):

| Узкое место | Решение | Эффект |
|---|---|---|
| диск IDE читался по сектору в режиме PIO | DMA через bus-master, по 64 КБ | чтение 6.7 → 60 МБ/с |
| FAT: запрос на каждый кластер | непрерывные цепочки кластеров одним запросом | |
| FAT: две копии таблицы в одной строке кэша, 2 чтения + 2 записи на кластер | LRU-кэш, отложенная запись таблицы, буфер записи 64 КБ | запись 4 МБ: 3.3 с → 0.1 с |
| запуск программы обнулял всю арену (до 512 МБ) | арена без обнуления, обнуляются только крупные блоки при выдаче (как свежие страницы Windows) | 184 → 37 мс |
| `invlpg` на каждую из десятков тысяч страниц арены | один сброс TLB для больших диапазонов | 37 → 16 мс |
| `strlen`, `memchr`, `memcmp` по байту | по машинному слову | ×2.4 |
| `printf` с плавающей точкой: `fyl2x` и преобразование x87 на каждую цифру, потеря точности при 53-битном FPU программ | 17 значащих цифр одним 64-битным целым в расширенной точности | точные цифры как в msvcrt |
| `hal_ticks_ms` с `cli/sti` и 64-битным делением на каждый вывод в терминал | чтение счётчика без блокировки | вывод в терминал +33% |
| любое событие будило все ждущие потоки всех процессов, чтобы они перепроверили условие | ожидание описывает, чего ждёт поток; планировщик проверяет сам | простой Chromium: 10000 → 1300 переключений/с |
| рабочий стол спал до 8 мс между кадрами, даже когда у потока программы истёк таймер или пришли данные | сон стола прерывается, как только поток программы может работать | запуск Chromium до окна 21.5 → 16.5 с (QEMU без KVM) |
| большие DLL (chrome.dll ~280 МБ) читались и перемещались целиком до запуска | страница читается и перемещается при первом обращении, кэш общий для процессов и остаётся после выхода | повторный запуск Chromium 5.5 с |
| `BitBlt` кадра Chromium: цикл по пикселям с 64-битным делением на каждый | копирование строк | 12.5% → 0.5% процессора при прокрутке |
| компоновщик рисовал обои и окна под непрозрачным окном | рисование начинается с верхнего окна, закрывающего область | |
| 41 КБ состояния процесса копировались туда и обратно при каждом переключении | крупные таблицы в куче программы | memcpy 8.6% → 4.1% при прокрутке |
